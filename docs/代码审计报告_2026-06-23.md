## 二、严重问题（建议立即修复）

### 2.1 `ui/main_window.py` 严重膨胀 — 3881行

**严重程度：** 🔴 高

`MainWindow` 单个类承担了所有UI逻辑、业务逻辑、配置管理、撤销恢复、批量操作、发运主体定义管理、预设管理等职责。这是典型的上帝类（God Class）反模式。

**影响：**
- 难以维护、难以测试
- 任何小修改都需要理解整个3800行上下文
- 新人上手成本极高

**建议：** 拆分为多个 Mixin 或独立类：
- `TreeOperationsMixin` — 树结构操作（刷新、展开、折叠、隐藏）
- `ShippingConfigMixin` — 发运配置操作（批量设置、快捷键、格式刷）
- `UndoRedoManager` — 撤销/恢复状态管理
- `EntityDefinitionManager` — 发运主体定义管理
- `PresetManager` — 预设管理
- `ProgressManager` — 工作进度保存/加载

## 三、中等问题

### 3.1 BOMNode.__post_init__ 自动计算的副作用

**严重程度：** 🟡 中

[BOMNode.__post_init__()](models/bom_node.py#L45-L48) 在创建节点时自动调用 `calculate_final_quantity()`。但此时 `parent` 可能还未设置，导致计算结果不正确。

在 `tree_builder.py` 的 `add_child()` ([bom_node.py:134-145](models/bom_node.py#L134-L145)) 中，设置 parent 后再次调用 `calculate_final_quantity()` 来修正。这意味着每个节点被创建时都会计算一次错误值，然后被正确值覆盖。

**影响：** 轻微的性能浪费，且如果有人忘记调用 `add_child()` 而直接设置 parent，最终数量会错误。

**建议：** 移除 `__post_init__` 中的自动计算，改为在 `add_child()` 和 `build_from_dataframe()` 完成后统一调用。

---

### 3.2 undo/redo 状态恢复的 material_id 冲突风险

**严重程度：** 🟡 中

[main_window.py:1461](ui/main_window.py#L1461) 中 `_restore_state` 使用 `material_id` 作为 key 查找节点：
```python
current_map = {n.material_id: n for n in self.tree_builder.all_nodes}
```

但同一个 `material_id` 可以在不同父节点下出现多次（BOM 数据特性）。如果两个同 material_id 的节点一个被删除一个被保留，恢复时只能找到其中一个。

**建议：** 使用 `f"{parent_id}_{material_id}"` 作为 key，与 `_save_state` 中的 key 生成方式一致。

---

### 3.3 tree_builder.py 中 node key 使用全局计数器

**严重程度：** 🟡 低

[tree_builder.py:107-109](core/tree_builder.py#L107-L109) 使用 `f"n{node_counter}"` 作为唯一 key，`nodes` 字典实际上只用于第二遍挂载时查找，之后不再使用。`self.nodes` 保存了所有节点但 key 是无意义的 "n0", "n1" 等，与 `all_nodes` 列表完全重复。

**建议：** 可以简化为只用 `parent_key_map` 和 `all_nodes`，去掉 `self.nodes` 字典。

---

### 3.4 exporter.py 中 openpyxl 样式逐单元格设置

**严重程度：** 🟡 低

[exporter.py:181-213](core/exporter.py#L181-L213) 在循环中逐行逐列设置边框、对齐等样式，当数据量大时性能较差。

**建议：** 可以考虑使用 openpyxl 的 `NamedStyle` 预定义样式对象复用，或使用批量设置。

## 四、代码风格与规范问题

### 4.1 异常处理过于宽泛

多处使用裸 `except` 或 `except Exception`：

- [main.py:21-22](main.py#L21-L22): `try: ... except: pass` — 捕获所有异常并静默忽略
- [main.py:121-122](main.py#L121-L122): 同上
- [main_window.py:3081](ui/main_window.py#L3081) 等多处: `except Exception as e` 用于文件操作

**建议：** 至少记录异常信息到日志，避免静默吞掉错误。

---

### 4.2 变量命名中英混用

[exporter.py:195-196](core/exporter.py#L195-L196):
```python
物料号_cell = ws.cell(row=row, column=2)
if 物料号_cell.value == '发运主体':
```

使用中文变量名 `物料号_cell` 不符合 Python 社区惯例，虽然合法但降低可读性。

---

### 4.3 main_window.py 事件过滤器过于复杂

[main_window.py:254-321](ui/main_window.py#L254-L321) 的 `eventFilter` 方法承担了多种职责（双击展开/折叠、单击菜单、复选框点击、Shift 范围选择），逻辑分支超过 60 行。

**建议：** 拆分为多个独立的事件处理方法。

## 六、安全与稳定性

### 6.1 文件操作

- 文件路径使用 `Path` 对象，基本安全
- 导入文件时未做文件大小限制，超大文件可能导致内存问题
- Excel 文件使用 openpyxl 引擎，安全性可接受

- 物料号、发运主体等输入未做格式校验（如 SQL 注入不适用，但可能存在特殊字符导致 Excel 写入异常）

- 全局异常钩子 ([main.py:71-80](main.py#L71-L80)) 只记录日志不弹窗
