## 二、打包阻塞级问题（P0，已核实）

### P0-1 PyInstaller onefile 下配置写入静默丢失

- **位置**：`core/entity_config.py:82-84`（路径定义）、`:275`（save_definitions）、`:328`（save_presets）；同样影响 `core/progress_config.py:24-27`、`main.py:25-35`（error.log）
- **核实情况**：已读源码确认。`config_dir = Path(__file__).parent.parent / 'config'`，onefile 下 `__file__` 解析到 `%TEMP%\_MEIxxx\`。spec 的 `datas=[('config','config')]` 把默认配置解压到该临时目录，**读取正常**；但 `save_definitions`/`save_presets` 写入也落到临时目录。全代码库 grep 确认**无任何 `sys._MEIPASS`/`frozen` 处理**。
- **触发场景**：用户在"发运主体设置"里改名/新增实体或保存预设 → 提示"保存成功" → 程序退出后临时目录被系统清空 → 下次启动恢复默认。**无任何报错的静默数据丢失。** 对一个核心用途就是"维护发运配置"的离线工具，这是发布阻塞项。
- **修复方向**：读写分离——内置默认从 `sys._MEIPASS` 只读加载，用户写入落到 exe 所在目录或 `%APPDATA%`（依据 `getattr(sys, 'frozen', None)` 判断）；或改用 onedir 打包规避（但会放弃单文件 EXE）。

### P0-2 静态缓存格式契约不一致，导出发运单出现"双前缀"主体名

- **位置**：`core/entity_config.py:136-146`（get_static_entity_map）、`:284-292`（get_entity_map 返回带前缀值）、`:112-133`（get_entity_display_name 再拼一次前缀）；出口 `core/calculator.py:90-92`、`core/exporter.py:322`
- **核实情况**：已读源码逐行确认。`get_static_entity_map()` 首次调用用 `get_entity_map()` 填缓存，值为**带前缀**的 `{"01":"01-机头"}`；而消费方 `get_entity_display_name('01')` 假定缓存值是不带前缀的纯名称，又执行 `f'{code}-{name}'` → 返回 **`"01-01-机头"`**。该值经 `calculator.py:90-92` 写入"发运主体名称"列 → 最终发运单（`calculator.py:135`）的"发运主体"列。界面层代理**实测新会话首次调用返回 `'01-01-机头'`**。
- **隐蔽性**：UI 树/下拉框走 `main_window._get_entity_display_name`（`main_window.py:165-166`）优先用 `self.entity_map` 实例映射（单前缀，正确），**界面显示完全正常**——只有预览表和导出的发运单错。除非用户在本次会话内手动保存过实体定义（走 `update_entity_name_map` 的正确格式"自愈"缓存），否则每次全新启动必现。
- **修复方向**：`get_static_entity_map()` 改为存 `{code: name}` 无格式分歧的映射（或在 `get_entity_display_name` 内对缓存值剥前缀归一化）；顺手把 `main_window.py:22` 已 import 却从未在启动时调用的 `update_entity_name_map` 接上。

## 三、撤销系统系统性缺陷（P1，建议随版本重建）

v2.2 声称用复合 key（parent_id_material_id）修复了撤销冲突，**实际不充分**，且存在多个关联缺陷：

| # | 位置 | 问题 |
|---|------|------|
| 1 | `ui/undo_mixin.py:18-21`、`ui/batch_mixin.py:481-494` | **key 冲突**：拆分物料产生的 node2 与原节点同 `parent_id+material_id`，快照字典互相覆盖 → 拆分后任何撤销/恢复都会丢失或错置其中一个节点。复合 key 也无法区分 ERP 中同 (物料,父) 对的多实例 |
| 2 | `ui/undo_mixin.py:84-153` | **幽灵节点**：`_restore_state` 不清理"快照中没有的多余节点"。撤销"添加/拆分"后，被添加的节点仍留在 `all_nodes`（无父、不显示，但参与计算/保存/统计）→ 污染后续所有结果 |
| 3 | `ui/progress_mixin.py:61-84,137-184` | **跨数据集撤销**：导入 BOM/加载进度不清空撤销栈，换数据集后按撤销会把旧数据快照复活进当前 `all_nodes` → 数据污染 |
| 4 | `ui/batch_mixin.py`（batch_config/add_material_row）、`ui/main_window.py:693-703`、`ui/config_mixin.py:222-251` | **半数变更入口既不 `_save_state` 也不置 `_dirty`**：这些操作无法撤销；且操作后关窗不提示"未保存"直接退出 → 静默数据丢失 |
| 5 | `ui/config_mixin.py:429-443`、`:357` | **重复快照**：一次操作存两个相同快照 → 撤销第一次无任何可见效果，用户以为撤销坏了 |

**建议**：一次性把快照键换成 tree_builder 已有的行级唯一 key（`nodes` 字典的 `n{i}` 或 `id(node)`）；`_restore_state` 补删除逻辑；数据集切换清栈；所有变更入口统一走"快照+dirty+标题更新"包装函数。

## 四、数据正确性问题（P1）

| # | 位置 | 问题与触发场景 |
|---|------|--------------|
| 1 | `core/calculator.py:76-87` | **总重错误**：`净重:'first'` 后又 `总重 = 求和数量 × first净重`。同物料在不同父节点下净重不同时（ERP 常见），总重偏离真实值。建议总重直接对原列求和 |
| 2 | `core/calculator.py:122` | **数量强制取整 + 银行家舍入 + NaN 溢出**：小数数量（电缆米数）被截断；`round` 是银行家舍入（0.5→0）；NaN 经 `astype(int)` 变成巨大负数垃圾值。建议保留小数、NaN 显式报错 |
| 3 | `models/bom_node.py:125-136` + `core/tree_builder.py:141-148` | **递归数量依赖输入行序**（三层审查交叉印证）：`add_child` 只重算直接子节点、不级联后代。若 BOM 非拓扑序（子节点行排在父节点前），子树静默丢失祖先乘数，数量算错且无报错。ERP 导出通常有序故当前未暴露。建议建树后做一次后序全树重算 |
| 4 | `core/bom_parser.py:266-267` | **规格列被无条件覆盖**：`df['规格'] = split_results['spec']` 忽略原值（与图号列"仅空值填充"处理不一致）→ ERP 自带规格列被清空 |
| 5 | `core/bom_parser.py:255-259,413-437` | **空表格/缺列崩溃**：0 行 DataFrame 触发 KeyError；必需列缺失抛英文 KeyError 堆栈 |
| 6 | `core/bom_parser.py:354-355` | **CSV 只支持 utf-8-sig**：很多 ERP 的 CSV 是 GBK/GB18030 → 导入即 UnicodeDecodeError 崩溃。建议编码回退 |
| 7 | `core/progress_config.py:149-160` | **进度恢复首匹配 break**：拆分物料保存后重新加载，第二个拆分节点的主体/方式/备注全部丢失 |
| 8 | `core/progress_config.py:107-116` + `ui/progress_mixin.py:158-168` | **项目信息表 NaN 残留**：历史 nan 修复只覆盖了 BOM 数据表，"项目信息"工作表未 fillna → 空字段读回为 "nan" 灌入输入框并随导出带出 |
